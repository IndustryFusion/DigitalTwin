# Design

## Context

See proposal.md - Why. The repository holds many independently built components
with long-running CI (`Build`, `K8s tests`, about 50 minutes each), Markdown issue
templates, and no root `.gitignore`, `CONTRIBUTING.md`, pull request template or
central architecture document. The plan was agreed on issue #932.

## Goals / Non-Goals

**Goals:**
- Use OpenSpec's native schema, commands and skills; add only configuration,
  instructions and documentation around them.
- Keep specifications agent-independent; agent-specific files are generated by
  `openspec init` and point at shared instructions.
- Let existing components keep working without specifications.

**Non-Goals:**
- Custom OpenSpec schemas or tooling.
- Writing a new architecture document, or seeding `openspec/specs/` from the
  existing code (possible follow-up issues).

## Decisions

**Default `spec-driven` schema.** Its proposal → specs → design → tasks artifacts
already separate requirements from implementation decisions. Alternative: a custom
schema with an explicit approval artifact; rejected as unnecessary infrastructure.

**A specification only where it pays off.** Features, behaviour visible to users
or other components, and contracts between components are specified first. Research
with an open outcome is explored first and specified from the result, because a
specification written earlier would be rewritten repeatedly. Bug fixes and
maintenance need an issue only; a bug fix adds a scenario when it exposes a broken
contract. Alternative: a specification for every change; rejected as ceremony
without benefit for dependency updates and similar changes.

**Specifications grow with changes.** `openspec/specs/` starts with this workflow
only, and a capability gets its first specification when a change touches it.
Alternative: specifying existing components up front; rejected as expensive and
likely to go stale unnoticed.

**Capability paths.** `contracts/<name>` for contracts between components and
`<component>/<name>` for one component, so that a change is easy to locate. Nested
paths were tried with `openspec validate --strict` and `openspec archive`.
Alternative: a flat list; rejected because the repository has many components.

**One Pull Request per change, gated by a `spec-approved` label.** The agent first
pushes only `openspec/changes/<id>/`; a maintainer reviews and adds the label; any
maintainer may do so. Implementation commits follow in the same Pull Request.
Alternative: separate specification and implementation Pull Requests; rejected as
extra overhead. Commits stay distinguishable in history.

**Specification-only contributions run only the OpenSpec validation.** Both triggers
of `Build` and `K8s tests`, `push` and `pull_request`, get `paths-ignore: openspec/**`,
as decided on the issue. A specification doesn't change what these workflows test, and
they take about 50 minutes each. GitHub skips a workflow only if all changed files
match, so an implementation Pull Request with code still runs both. `workflow_call` has
no path filter, so the nightly run is unaffected. No status check is required on `main`,
so a skipped workflow doesn't block a merge. Alternative: leaving the workflows
unchanged; rejected because it costs runner time without any signal.

**Traceability by naming and a proposal line.** Change IDs
`gh-<issue>-<kebab-summary>` plus `Issue: #N` in `proposal.md`, stated in the
`openspec/config.yaml` rules and the pull request template. Alternative: a GitHub
integration service; rejected (minimal infrastructure).

**The archive closes the issue.** Archiving is the last lifecycle step, so the issue
stays open until then, which also makes a forgotten archive visible. Pull Requests
proposing or implementing a change use `Refs #N`; the commit archiving the issue's
last change carries `Closes #N`. An issue can have several changes, so an archive
closes it only if no other change for that issue is open or planned. Changes without
a specification have no archive, and their Pull Request closes the issue as usual.
All merge methods enabled on this repository keep the keyword in the commit message.

The rule goes into `operations.archive.guidance` in `openspec/config.yaml`, which
the archive skill reads at runtime, and into `AGENTS.md` and `CONTRIBUTING.md`.
Alternatives: editing the generated `openspec-archive-change` skill, rejected because
`openspec update` overwrites it and it covers only one agent; closing at the merge of
the implementation, rejected because the archive would then be easy to forget.

**`AGENTS.md` as the single instruction source.** Most coding agents read it
natively; `CLAUDE.md` points to it. Claude Code is the starting agent with native
skills and `/opsx:*` commands; others are added with `openspec init --tools <id>`.

**Only official files in `.claude/`.** The generated OpenSpec files are tracked. A
tracked `.claude/.gitignore` keeps `settings.local.json` and `worktrees/` out. The
directory is not ignored as a whole, because the official files have to be tracked.
Contributors keep personal skills in `~/.claude/skills/`.

**CI installs a pinned, checksum-verified standalone binary.** A fixed release asset
is downloaded and its SHA-256 checked, with telemetry off. Alternatives: piping the
unpinned install script (content not pinned) or `npm install -g` (adds a Node
toolchain to the job).

**Project context references existing documents.** `openspec/config.yaml` links
`README.md`, the wiki and component READMEs instead of duplicating them, and states
nothing which is not already documented.

**A new capability's delta includes `## Purpose`.** Without it, `openspec archive`
writes a placeholder which `openspec validate --all --strict` rejects after
archiving, as seen in a trial. This is a rule in `openspec/config.yaml`.

## Risks / Trade-offs

- [Anyone with triage rights can add `spec-approved`] → Documented as a limitation;
  maintainers can add `CODEOWNERS` and branch protection later.
- [OpenSpec treats operation guidance as advisory, and the archive skill does not
  commit] → The rule is also in `AGENTS.md`, `CONTRIBUTING.md` and the pull request
  template; if an issue stays open by mistake, a maintainer closes it.
- [If `Build` or `K8s tests` become required checks, a skipped workflow would block
  merging specification-only Pull Requests] → Revisit the filter when adding them.
- [Specifications drift from the code] → Tasks include tests for the scenarios, and
  verification is reported per scenario in the Pull Request.
- [No central architecture document, so agents have less context] → Context links
  what exists; agents report conflicts rather than assume.
- [Pinned OpenSpec version ages] → Version and checksum are bumped in one place.
- [Green CI is not functional correctness] → The contributor guide lists the checks
  that require human review.
