# Design

## Context

`owl2instances.py` scans the hierarchical references of every instance and
type. Unless `-p/--properties` is given, it adds `opcua:HasProperty` to the
references it ignores, so no Property becomes an attribute, a sub-attribute or
a binding. Two of the four example makefiles pass `-p` (laser, type contracts),
two do not (pump, simple), and neither does the pump tutorial that the OPC UA
chain test runs. What a package holds therefore depends on which recipe built
it, and the recipe users copy — the tutorial — leaves out units, ranges and
nameplates.

With `-p`, the translation itself is in place and tested
(`test_reference_types_properties`, `test_interfaces`, the laser package):
this change only turns it on by default. The output with Properties equals what
`-p` writes at `main`.

## Decisions

### D1. Follow Properties by default, opt out with `--no-properties`

The default flips; `--no-properties` restores today's default output.

Alternatives:
- *Keep the default, pass `-p` in the pump and simple makefiles and the
  tutorial.* Fixes the examples, but every other caller keeps losing units
  silently, and the right output stays the one you have to know to ask for.
- *A tri-state `--properties {on,off}`.* More to type and document for no
  case the two flags do not cover.

### D2. Keep `-p/--properties` as a no-op

Scripts outside this repository pass `-p`. Rejecting it would break them for
no gain; it now means what the default means. It does not undo
`--no-properties` whatever the order, so a script that adds the opt-out to an
old command line gets the opt-out. Implemented as a separate option rather
than as `argparse.BooleanOptionalAction`, which would let the last of `-p`
and `--no-properties` win and would print "(default: True)" next to a flag
whose only purpose is compatibility.

Alternative: *remove `-p` with an error that names `--no-properties`.* Cleaner
help, but breaks existing build scripts for a purely cosmetic gain.

### D3. Sub-attributes are declared in the shapes only

`entities.ttl` declares an attribute with `rdfs:domain <type>` for members of
entity types. A Property of a variable is not a member of an entity type but
of a variable type, so it gets no declaration there, with or without `-p`.
Clients that need the sub-attributes of a variable read the nested
`sh:property` of the variable's property shape. This change documents that
and adds no declarations: adding them would give `entities.ttl` a second,
weaker description of what the shapes already constrain, and a domain for
`opcua:hasEngineeringUnits` would have to be an attribute, which is not a
class.

### D4. The package check is a SPARQL ASK on the generated shapes

`kms-packages-check` runs `tests/kms-packages/pumps-engineering-units.query`
against `opcua-pumps/shacl.ttl` with the query helper the `owl2instances`
tests already use. It names one concrete analog variable
(`pumps:hasMotorTemperature` of `pumps:DriveMeasurementsType`, a
`BaseAnalogType` variable in the Pumps specification) rather than "any
`hasEngineeringUnits`", so it fails if the property lands in the wrong place,
not only if it is missing. A `grep` on the package's
`knowledge/entities.ttl` checks the other half of D3: no
`hasEngineeringUnits` there.

Alternative: *a check in `semforge validate` or a pytest over the package.*
`validate` checks conformance, not content; a pytest would need the package,
which only the `opcua-kms-packages` job builds.

### D5. Tests and generated files follow the new default

- The golden file `test_pumps_instanceexample.instances` is regenerated; the
  pump shapes are not compared (`.nocompare` as before). Every other golden is
  unchanged, because those nodesets either have no Properties or were already
  run with `-p`.
- `test_interfaces` drops `-p` (the default covers it).
  `test_reference_types_properties` keeps `-p`, so its unchanged golden shows
  that `-p` changes nothing. A new case `test_reference_types_no_properties`
  runs the same nodeset (a symbolic link) with `--no-properties` against a
  golden without `test:hasMyProperty`.
- `tests/corpus/opcua-pumps` of the SemForge SDK stays as it is. It is a
  fixed slice of an older chain output (earlier entity ids, five knowledge
  files, a hand-added `hasTestAttribute`), not regenerated by any build.
  Re-slicing it from today's chain fails two of the six VS Code e2e tests of
  `25-opcua` already without Properties (the `rdf:JSON` list warning times
  out, and the Main page does not bring an entity into view), while the
  current slice passes all six; with Properties the SemForge type pages of the
  slice also become about six times slower (all type pages 73–79 s without,
  459 s with). Both are SemForge matters of their own and are left to a
  follow-up; this change does not touch the SemForge SDK.
- The OPC UA chain test and the tutorial expect 22 entities and 64 bindings;
  the message check expects 53 distinct attributes sent (11 nodes are unset in
  the example nodeset: the 6 of before and 5 Properties of the technical data
  file), a sent `devices:hasManufacturer`, and nothing for the unset
  `opcua:hasSize`.

## Size and time

Measured on the pump example (8 cores, Python 3.12, one run each):

| | without Properties | with Properties |
|---|---|---|
| `owl2instances.py` | 49 s | 72 s |
| `shacl.ttl` | 0.57 MB | 2.65 MB |
| `model-instance.jsonld` | 27 KB | 58 KB |
| package | 13 MB | 16 MB |
| `semforge verify` / `validate` | 8 s / 17 s | 10 s / 26 s |
| constraints evaluated by `validate` | 1986 | 2759 |
| `shacl2flink` `make build` | 111 s, 92 MB output | 170 s, 115 MB output |
| SemForge: every type page of the corpus slice | 79 s | 459 s |

`kms-packages-check` checks the units with one SPARQL ASK and one `grep`; both
take under a second.

## Risks

- **Consumers of the default output see more attributes.** That is the point
  of the change; `--no-properties` restores the old output. Anyone rebuilding a
  package with the old recipe gets the new attributes, and the pump tutorial's
  dataservice sends 18 more values.
- **Bigger shapes make shacl2flink and SemForge slower on OPC UA packages.**
  Measured above. No Build job compiles the pump package with shacl2flink;
  the SemForge slowdown on type pages is a follow-up for the SDK.

## Conflicts

None with existing specs. `contracts/opcua-live-data` names the number of
bindings in a scenario; the delta updates the number, the rule stays.
`opcua/instance-declaration-shapes` already describes a Property of an added
variable (`hasEngineeringUnits`) as constrained like one of a type, which with
this change is what the default output does.
