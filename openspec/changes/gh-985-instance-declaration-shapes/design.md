# Design

## Context

See proposal.md for the motivation. The current state of the three components:

- **opcua.** `owl2instances.py` builds one node shape per type. For an object child it scans the child's *type*, never the child's instance declaration, so members a declaration adds are dropped. `lib/owlbuilder.py` (used by `owl2vt.py`) already decides when a declaration extends its type: an object declaration with local children of its own needs its own identity (`_resolve_target`).
- **shacl2flink.** `sh:node` is resolved by substitution before translation: the referenced shape's triples are copied to the referring node, with no change of focus node. A property shape underneath `ngsi-ld:hasObject` therefore becomes a sub-attribute chain of the *referring* entity (`hasLink` → `hasObject` → `hasLevel`); the level guard never admits a row, because no attribute is named `hasObject`, so the check compiles but never raises. `sh:class` on a relationship already joins the referenced entity, but only to read its type (`sql_check_relationship_base`: entity `C`, class lookup `G`). All aliases of that join are pinned with `STATE_TTL '0d'` and mini-batch is off; since updates replace rows and deletions remove keys, the pinned state is bounded by the live model.
- **SemForge SDK.** pyshacl validates the whole model as one graph, and shapes referenced through `sh:node` are added to the shapes it runs, so the nested form already validates correctly. pyshacl reports one `NodeConstraintComponent` result on the referring attribute and the inner results only as `sh:detail`, which the SDK never reads. The shape page computes reach only from a top-level `sh:node`.

## Goals / Non-Goals

**Goals:**
- One form of nested shape, generated by opcua and evaluated with the same meaning by pyshacl (SemForge) and by the streaming checks (shacl2flink).
- The streaming check reuses the existing relationship-join pattern and its state pins, so its state behaves like that of the existing relationship checks.
- Nothing underneath `ngsi-ld:hasObject` is ever compiled into a check that cannot raise.

**Non-Goals:**
- A general focus shift for arbitrary SHACL paths in shacl2flink; only `sh:node` on the object of a relationship, one level.
- New alert formats or alert routing.

## Decisions

### D1 Nested node shape through the relationship
The owning type's property shape for the relationship gets, on its `ngsi-ld:hasObject` value shape, `sh:node <declaration shape>` next to the existing `sh:class <child type>`. The declaration shape has no target and constrains only the members the declaration adds.

Alternatives considered:
- *Virtual types* (a generated subclass per declaration, assigned to the child entity): per-entity validation without joins, but it changes entity types, which every type-based query and the contract see; rejected by the issue's scope.
- *`sh:sparql` constraints*: shacl2flink already joins across entities for them, but they are opaque to SemForge's constraint model and need their own join pinning; rejected.
- *Inlining the members into the child type's shape*: wrong meaning, it would require them of every instance of the generic type.

### D2 The violation belongs to the owning entity
The requirement comes from the owning type's instance declaration hierarchy; the child entity conforms to its own type. pyshacl reports the result on the owning entity, and the existing cross-entity checks of shacl2flink (`sh:class` on relationships, `sh:sparql`) do the same, so the streaming check raises its alert on the owning entity too.

Alternative considered: alert on the child entity (more local, but contradicts the SHACL result and the offline validation in SemForge).

### D3 One alert per relationship instance, cause in the text
The event is `NodeConstraintComponent(<path>[<index>])`, following the existing event naming. The alert is open while any inner constraint is violated. Its text lists every violated inner constraint (kind and attribute) and the referenced entity, ordered by constraint identity, so the path to the cause can be reconstructed and the text is deterministic.

Alternative considered: one alert per inner constraint (finer, but more alerts and more state, and it diverges from the single SHACL result).

### D4 One relationship hop; deeper additions summarised per type
The generator emits declaration shapes only for additions in a direct child object. Additions deeper down are collected per owning type and reported once per type with their count and browse paths. shacl2flink rejects a declaration shape that again applies `sh:node` to a relationship's object.

Alternative considered: unlimited depth in the generator. pyshacl could validate it, but every further hop is another stream join with its own state and retraction paths, and SemForge and shacl2flink would then disagree on the same package.

### D5 Detecting additions in the generator
A declaration adds a member when the member's browse name is not among the declarations of the child's type and its supertypes. The detection follows the rule `lib/owlbuilder.py` applies (local children beyond the type). The declaration shape's properties are produced by the same code that produces a type shape's properties from declarations, applied to the added members only, so modelling rules, data types and value ranks behave exactly as for type-defined members. Its IRI is derived deterministically from the owning type and the declaration's browse path, so that packages stay reproducible.

Alternative considered: calling `owlbuilder` directly. It writes OWL axioms as a side effect and works on the Semantic Bridge graph rather than the shape builder; sharing the rule, not the class, keeps the two tools independent.

### D6 Streaming translation in shacl2flink
- Substitution of `sh:node` stays for its existing uses (node level, same focus). A reference on the `ngsi-ld:hasObject` value shape is excluded from substitution and translated as a *relationship node check*.
- The declaration shapes hold circuits, not only leaves: the OPC UA ValueRank form is an `sh:or` of a scalar and a list branch, and only the circuit evaluates it correctly (one branch always fails). So the declaration shape is compiled as an ordinary shape, through the existing rows, circuit and leaf templates: it is cloned onto a synthetic target class per (owning class, relationship), subclasses of the owning class included, and the relationship and property statements are rendered a second time over a *node focus* -- the entities such a relationship refers to, typed with the synthetic class. Inner constraints therefore mean exactly what they mean on an entity's own attributes.
- The circuit tops of the declaration shape feed a `NODE` edge into one node row per synthetic class instead of publishing. One generic statement for all node checks groups the violated tops per (owning entity, relationship instance) and raises `NodeConstraintComponent(<path>[<index>])` on the owning entity; the node row publishes it.
- The node focus types the object of every live relationship with the synthetic class of its owner's type and the relationship; the bases' pinned join on the target class keeps the classes that have constraint rows. It does not join the node rows itself: Flink pushes the focus's grouping below such a join and the pin of the node rows is lost, so the check died once the job was older than the state TTL (measured on the local cluster).
- The node statement joins the owning entity, its relationship rows, the node rows and the members' verdicts, all pinned `'0d'`, and the grouped step pins its accumulator, so the set of violated constraints can shrink and grow by retraction. The group key is the relationship instance, not the referenced entity, so re-pointing a relationship updates the alert instead of moving it; the owner's `deleted` flag is read as an aggregate, as the counts do.
- The text is deterministic without an ordered aggregate (Flink's `LISTAGG` has none): each member's rank among the members of its node row, taken from the edge list, is a static position, and the text concatenates one slot per position.
- A deleted or missing referenced entity stays in the node focus with no live attribute rows, so its required members evaluate as absent.
- The build rejects: a property shape directly underneath `ngsi-ld:hasObject`; a declaration shape containing another `sh:node` on a relationship's object, `sh:sparql`, `sh:not`, `sh:xone` or an inverse path (none of them is evaluated over the node focus); a declaration shape that produced no constraint; a relationship that is not a property of a node shape with `sh:targetClass`.
- A circuit level that evaluates against the entities (because the package has `sh:not` or `sh:xone` on it) cannot see the synthetic classes, so the node checks' circuit nodes on such a level get one more statement that reads the members' verdicts.
- The extra statements (two over the node focus, the node statement, and that one per affected level) are emitted only when a node check exists, so every other package compiles to the same SQL as before.
- SQLite gets the same templates, so the SQLite and Flink checks raise the same alerts.

Alternatives considered:
- *Extend the relationship base with joins to the referenced entity's attributes and compile the inner constraints as leaves keyed by (owning entity, relationship index)* (the first plan): fewer statements, but the leaves would bypass the circuit, and every declaration with a ValueRank would report the branch it does not use.
- *Compile the inner checks as separate alerts on the referenced entity and derive the owner's alert from them*: needs a second alert hop (alerts as input) and breaks D2. The node statement reads the internal verdicts of the circuit instead, which never become alerts.

### D7 SemForge: read the cause, follow the reach
- The validation adapter reads `sh:detail` recursively and attaches the inner results to the outer result as its cause; the outer result keeps its identity (referring shape, relationship, node constraint), so expectations, coverage and counts are unchanged.
- The report and the editor's violation display (entity pages, Problems panel) show the cause.
- The shape page's reach follows `sh:node` on value shapes of property shapes: the referenced entities of the referring entities' relationships reach the declaration shape.
- The constraint enumerator keeps the outer identity and does not enumerate inner constraints separately.

Alternatives considered:
- *Report the inner results as separate violations* on the referenced entity: they would be visible without a cause view, but they change the identity and count of the violation, contradict D2 and disagree with the single alert of the streaming check.
- *Show only the outer result*, as today: no change in the SDK, but the reader cannot see which attribute is wrong, which is the purpose of D3's text in the streaming alert.

### D8 Verification
- **Generator:** a new case in the owl2instances suite (direct additions, an addition two relationships deep, a declaration without additions), compared against expected shapes and validated with pyshacl; unit tests for addition detection and the summary report.
- **Generator to compiler:** the generated shapes of that case are compiled by shacl2flink in the existing opcua-shapes test, and SQLite results are compared with pyshacl in the pyshacl comparison.
- **shacl2flink:** SQL cases for every scenario of its spec in the SQLite suite; build-time rejection tests.
- **End to end:** the throwaway e2e KMS used by `make test-flink-e2e` gains an owning type with a declaration shape; the bats suites raise, clear, delete the referenced entity and change its attributes, through Kafka and through the NGSI-LD API to Alerta. `tools/ttl_test.py` gets a family for the check (raise, retract, referenced entity deleted, after three times the state TTL idle).
- **SemForge:** unit tests for the adapter and reach; a corpus package with the nested form; the editor shows the cause.
- **Coverage:** each component keeps its 80 % gate, and the changed code is measured and stated in the PR.

Alternatives considered:
- *SQLite cases only for the streaming check*: fast and deterministic, but they do not exercise Flink's state, retraction and the alert path, where cross-entity checks are most likely to fail.
- *End-to-end tests only*: they cover the user-visible result, but are slow and do not pin down every scenario; the SQLite cases and the pyshacl comparison keep each scenario cheap to check.

### D9 datasetId alignment
`datasetId` stays the key of attribute instances: it is NGSI-LD's own construct for several instances of one attribute, each addressable on its own and with its own `observedAt` and history, which is what an element of a placeholder needs. Placeholder members added by a declaration are therefore constrained per `datasetId` like type-defined placeholders (class per instance, count of distinct `datasetId`s, the default instance counting as one), and the relationship node check is keyed by the relationship's `datasetId` (D3).

The offline models must keep instances apart for these checks to be testable: today the model query attaches a `datasetId` to an attribute through the attribute's value, so an instance without a `datasetId` is merged into an instance with a `datasetId` and an equal value. The query correlates the `datasetId`, the value and the other sub-attributes through the attribute instance itself, for properties, relationships, list and JSON properties.

Alternatives considered:
- *An attribute name per element* (`hasItem1`, `hasItem2`): no shared path to constrain, and an unbounded vocabulary.
- *One list relationship holding all elements*: no identity, metadata or history per element; every change rewrites the list.
- *Keep the value correlation and deduplicate by value and `datasetId` afterwards*: still wrong when instances have equal values, which is exactly the case to support.

### D10 Placeholder membership
An OPC UA instance does not refer to the declaration it instantiates, so the generator has to decide which children of an entity are instances of a placeholder. The only evidence is the child's browse name against the placeholder's pattern, and its type. For a pattern with a fixed part (`Item<no>` → `Item[a-zA-Z0-9_-]+`, matched as a whole) the name decides, and the declaration shape's `sh:class` then checks the type, so a wrong type is reported. For a fully generic placeholder (`<Part>`, any name) the name carries no information; the type decides, as for placeholders defined by types today. This is a limitation of OPC UA placeholders, not of the shapes, and the documentation says so.

Alternatives considered:
- *Membership by name only*: reports wrong types for named patterns, but for a fully generic placeholder every unrelated child becomes an instance and is reported against the placeholder's type.
- *Membership by type only* (as for type-defined placeholders): no false reports, but a wrong type is never counted as an instance, so it is never reported, even where the name says it is meant to be one.

## Risks / Trade-offs

- [Pinned state never expires: a lost retraction leaves a row forever] → same risk as every pinned join today; covered by the ttl_test family and the resync, which repairs missing rows.
- [State growth from the referenced entities' attribute rows] → bounded by the live model, as for the existing relationship joins; the inner path names are pushed below the join, so only constrained attributes enter state.
- [Alert updates when the set of violated inner constraints changes the text] → one open alert updates its text instead of closing and reopening; acceptable, and deterministic ordering prevents churn from ordering alone.
- [**BREAKING**: shapes that relied on the silently accepted form now fail the build] → the corpora in the repository (KMS packages, test fixtures, the opcua shapes test) are compiled during implementation; any hit is fixed in the same change.
- [Keeping instances apart changes expected results of existing offline cases that had equal values across instances] → those cases are reviewed one by one in the change; every changed expectation must match pyshacl.
- [Excluding `hasObject` references from substitution could change existing shapes] → only references on a `ngsi-ld:hasObject` value shape are excluded; node-level and same-focus `sh:node` keep their current translation, covered by the existing tests.

## Migration Plan

No data migration. Regenerated shapes are deployed as usual with the SHACL statement set; the new checks start raising once the statement set is redeployed. Rollback: redeploy the previous shapes and statement set.
