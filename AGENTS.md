# Agent Instructions

These instructions apply to every AI coding agent working in this repository. The
project uses [OpenSpec](https://github.com/Fission-AI/OpenSpec) for
specification-driven development. The human-facing version of this workflow is in
[CONTRIBUTING.md](CONTRIBUTING.md).

## Project context

- Purpose and architecture: [README.md](README.md). There is no central architecture
  document; read the README of the components a change affects.
- How each component is linted and tested:
  [build.yaml](.github/workflows/build.yaml),
  [k8s-tests.yaml](.github/workflows/k8s-tests.yaml).
- OpenSpec project context and artifact rules: `openspec/config.yaml`.

## Does the change need a specification?

| Change | Process |
|---|---|
| New feature, or behaviour visible to users or other components | Specification first |
| Change to a contract between components, e.g. message formats, topics or attribute forms | Specification first |
| Research or spike with an open outcome | Explore first, then write the specification from the result |
| Bug fix | An issue is enough. Add a scenario if the bug exposes a broken contract between components |
| Dependency updates, security fixes, chores | An issue is enough |

If you are unsure, ask. Do not specify existing behaviour a change doesn't touch.

## Lifecycle

GitHub Issue → Change proposal → Specification review → Implementation plan →
Implementation → Verification → Merge → Archive

1. **Propose.** Given a GitHub Issue, create a change with `/opsx:propose` (or the
   `openspec-propose` skill, or `openspec new change`).
   - Change ID: `gh-<issue>-<kebab-summary>`, e.g. `gh-42-add-alert-filtering`.
   - First line of `proposal.md` after the title: `Issue: #<number>`.
   - A delta for a new capability includes `## Purpose`.
2. **Inspect existing specs first.** Run `openspec list --specs` and read related
   specs with `openspec show <spec-id> --type spec`. Reuse existing capabilities
   instead of creating near-duplicates.
3. **Report conflicts.** If the issue conflicts with an existing spec or a contract
   between components, state it in `design.md` and in the Pull Request. Do not resolve
   it silently; present alternatives.
4. **Open the Pull Request with the proposal only** (`openspec/changes/<id>/`). Run
   `openspec validate <id> --strict` before pushing.
5. **Wait for approval.** Do not change source code until a maintainer has added the
   `spec-approved` label to the Pull Request. If it is missing, say that approval is
   pending and stop. Never add the label yourself.
6. **Implement** with `/opsx:apply` in the same Pull Request, working through
   `tasks.md` and ticking tasks as they are verified.
   - Create or update tests that cover the spec scenarios.
   - Never change approved requirements to fit the implementation. If a requirement
     cannot be met as written, stop, describe the conflict, and change the spec only
     after maintainer agreement.
7. **Verify.** Check every scenario in the change's delta specs against the
   implementation and report the result per scenario in the Pull Request. Passing CI
   does not prove functional correctness or security.
8. **Archive** after merge with `/opsx:archive <id>` in a follow-up Pull Request.

## Closing the issue

The issue stays open until its last change is archived:

- Commits and Pull Requests which propose or implement a change use `Refs #<issue>`,
  never a closing keyword.
- The commit archiving the issue's last change contains `Closes #<issue>`. The skill
  does not commit, so whoever writes the commit is responsible for this.
- If another change for the issue is open or planned, the archive commit uses
  `Refs #<issue>`.
- A change without a specification has no archive step: its Pull Request closes the
  issue directly.

## Rules

- Keep specification commits and implementation commits separate.
- Every Pull Request names its change ID, if it has one, and references its issue.
- Do not add runtime dependencies or infrastructure that the approved spec and design
  do not call for. No component's build, image or deployment may depend on OpenSpec.
- Do not invent architectural rules or test conventions that are not in the component
  documentation, `openspec/config.yaml` or an approved spec.
- In `.claude/`, only files generated by OpenSpec and officially maintained skills are
  tracked. Do not edit the generated files: `openspec update` overwrites them. Project
  rules for an OpenSpec operation go into `operations` in `openspec/config.yaml`.
